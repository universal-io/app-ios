# 調査記録: ハイライトの位置がズレる

作成: 2026-08-14 ／ ステータス: **解決。実機で確認済み**

読者: この経路を次に触るエンジニア。**原因の記録より、外し方の記録に価値がある**
文書なので、間違えた過程も残してある。

## 結論（先に）

原因は2つあり、**どちらもアプリの座標変換ではなかった**。

1. **送る画像が大きすぎた。** 実寸3024×4032ではモデルが座標を大きく外す
2. **座標をモデルに目測させていた。** 実測を渡す口はサーバーに最初からあった

修正は、**長辺1536への縮小**と、**OCRの実測矩形を`candidates`として渡すこと**。
実機で全ハイライトが対象に乗ることを確認した。

---

## 1. 何が起きていたか

iPhoneのカメラでMacの画面を撮り、AIが「押すべき場所」に枠を描くアプリで、
**枠が対象から下方向にズレていた**（目視200〜300px）。

**解説文は常に正しかった。** 画面の内容を正確に説明し、対処も合っていた。
**枠の位置だけが違う。** これは例外を出さないので、テストでは捕まらない。

## 2. なぜ3回も外したか

**症状から原因を推測して修正し、3回とも別のものを直した。**

| 試したこと | なぜ外したか |
|---|---|
| EXIF orientationを画素に焼き込む | 合成画像では実在するバグを再現・修正できたが、**実機写真は`exif_orientation=1`**で該当しなかった |
| 横向きレイアウトの変更（`AdaptiveSplit`） | 座標とは無関係。横持ちを悪化させた。巻き戻し済み |
| 仮説H1〜H5を立てて測定手順を設計 | **立てた5つの仮説はすべて外れていた。** 真の原因が候補に入っていなかった |

3回目は特に示唆的である。仮説を立てて測定手順まで定義したのに、
**仮説の集合そのものが、それまでと同じ前提から作られていた**ため原因を含んでいなかった。
「アプリの描画かモデルか」という二分は正しかったが、モデル側の中身を
「写真だと精度が落ちる」「画面領域基準で正規化している」としか想像できていなかった。

**効いたのは仮説ではなく、絵を見たことだった。**

## 3. 原因を確定させた測定

**サーバーが受け取ったバイトに、サーバーが返した座標で枠を描き、人間が見る。**
アプリを一切通らないので、結果はモデル単体の精度になる。

実装は [server/lib/debug-capture.ts](../server/lib/debug-capture.ts)（環境変数
`UIO_DEBUG_CAPTURE_DIR` が設定されているときだけ動く）と
[server/scripts/draw-boxes.py](../server/scripts/draw-boxes.py)。

```bash
cd server
UIO_DEBUG_CAPTURE_DIR=/tmp/uio-captures npm run dev
# 実機で1枚撮る
python3 scripts/draw-boxes.py /tmp/uio-captures/<request_id>
```

**1枚で決着した。** サーバー側の描画も、アプリの画面と同じ場所を指していた。
つまりアプリの描画は正しく、モデルの座標が違う。それまでの調査の半分が消えた。

**正確な誤差を読むにはグリッドを引くとよい**（画像に0.05刻みの横線を引いて数値を振る）。
目測で「200pxくらい」と言うより、`y_model ≈ y_true + 0.236` と出したほうが次が早い。

## 4. 原因1: 画像が大きすぎた

同じ写真をサイズだけ変えて送った結果:

| 送信サイズ | 枠が対象に乗った率 | 最大誤差 | 細かい文字の読み取り |
|---|---|---|---|
| 3024×4032（実寸） | **3/11** | +0.448 | — |
| 1512×2016 | 6/6 | 0.004 | `2026.6.880.0` 正確 |
| 1008×1344 | 6/6 | 0.005 | 正確 |
| 756×1008 | **16/16** | 0.004 | 正確 |
| 504×672 | 6/7 | 0.067 | 正確 |

**誤差はバイモーダルである。** モデルは当てる（0.01前後）か、大きく下に外す
（0.4前後）かのどちらかで、中間がない。**これは調整つまみではなく崖**なので、
定数オフセットでの補正は最悪手になる（当たっている回を壊す）。

`AnalysisSession.maxAnalyzedEdge` で長辺を1536に制限している。測定で完璧だった
1344と2016の間で、誤差の出た672から離れている値。

**注意: 大きさだけでは壊れない。** 合成UIを同じ3024×4032で送ると誤差0.000だった。
**写真であることと、大きいことの両方**が揃うと壊れる。だから合成画像だけで
測っていた間は、この原因は原理的に見つからなかった。

**そして「縮小すると数字を読み違える」という前提は逆だった。** これは
[server/lib/vision-model.ts](../server/lib/vision-model.ts) にコメントとして
書かれていた未測定の思い込みで、実際は1/6まで縮めてもバージョン番号を正確に読む。
アップロードは約4.5MB→0.2MBになり、体感速度も上がった。

## 5. 原因2: 座標を目測させていた

サイズを直しても、薄くて横長の低コントラストなコントロール（プルダウンなど）は
外した。実測で +0.049 — プルダウン本体ではなく、その直下の余白を囲んでいた。
**目で見て枠を描く限り、この誤差は消えない。**

**実測矩形を渡す口はサーバーに最初からあった。** `candidates` / `candidate_id` と、
「リストに該当があればその矩形をそのまま写せ」というプロンプト規則
（[server/lib/prompt.ts](../server/lib/prompt.ts) の `CANDIDATES_RULE`）。
Macコンパニオンがアクセシビリティから実測値を送る前提の設計で、
**アクセシビリティツリーが存在しないカメラモードでは空のまま**だった。

そこにOCRを繋いだ（[ios/.../TextGrounding.swift](../ios/UniversalIOCopilot/Services/TextGrounding.swift)）。
アップロードするのと同じバイトに対して`VNRecognizeTextRequest`を走らせ、
認識した文字列と矩形を候補として送る。

| 対象 | 実際のy | モデルの目測 | OCRの実測 |
|---|---|---|---|
| 切断 | 0.496 | 0.496 | 0.490 |
| トラフィックと DNS | 0.601 | **0.650** | **0.603** |

**これが精度を画像サイズから切り離す。** 座標が推定ではなく計測になるため、
カメラの解像度や画角が変わっても成立する。長辺1536という値は写真1枚から出た
マジックナンバーなので、そこに製品を預けたままにしない意味がある。

## 6. 残っていること

- **文字のないアイコンだけのボタンは候補に出ない。** 測るものが無いため。
  その場合はモデルの目測にフォールバックする（プロンプトが既にそう指示している）
- **枠がボタン全体ではなく文字に吸い付く。** 文字が枠で読みにくくなる。
  座標ではなく描画の問題なので、パディングか塗りの調整で対応できる
- **横持ちでの座標は未検証。** 回転そのものは
  `AVCaptureDevice.RotationCoordinator` で正立するようになったが、
  座標の精度は縦持ちでしか測っていない
- **タップで対象を指定する経路が繋がっていない。**
  `ContentView` の `pendingTap` はどこからも値が設定されず、常に nil のまま
  サーバーへ渡っている。測定では、タップ座標があると精度が上がる

## 7. 次に同種の問題を追うとき

1. **仮説を立てる前に、絵を見る手段を作る。** モデルが受け取ったものに
   モデルが答えた座標を描くだけで、探索空間が半分になった
2. **誤差は平均ではなく分布で見る。** 「毎回200pxずれる」に見えた症状は、
   実際には当たりと大外しの混在だった。平均だけ見ていると定数補正を入れて悪化させる
3. **コメントに書かれた未測定の前提を疑う。** 「縮小すると読み違える」は
   コードのコメントとして権威を持ってしまっていた
4. **既にある機構を探す。** 今回の本命の修正は、サーバー側は1行も足していない
