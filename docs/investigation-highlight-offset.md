# 調査: ハイライトの位置がズレる

作成: 2026-08-14 ／ ステータス: **未解決。測定待ち**

読者: 次に作業するエンジニア、および**この進め方が妥当か判断してくれる第三者**。
前提知識なしで読めるように書いてある。

## この文書が存在する理由

**症状から原因を推測して2回修正し、2回外した。** 1回目は実機に存在しない問題を
直し、2回目は別の箇所を壊した。原因を特定せずに触ったのが誤りだった。

そこで、**推測せずに故障箇所を確定させる測定手順**を先に定義する。

---

## 1. 何を作っているか（背景）

iPhoneのカメラで目の前の画面（Macの画面、券売機など）を撮り、AIに解析させて
**「押すべき場所」に枠を描き、操作を解説する**アプリ。

枠の位置は、AIが返す**正規化座標**（0〜1、画像左上原点の割合）で表現される。
これを表示上の座標へ変換して描画する。

## 2. 症状（正確に）

- **縦持ち**: 枠が対象からズレる。目視で200〜300ピクセル程度。
  直近の観測では「どこを指したいのか分からない」程度にズレていた
- **横持ち**: プレビューが横倒しの帯になり、正常に使えない（別問題。後述§7）

**解説の文章は正しい。** 画面の内容を正確に説明し、対処も合っている。
**枠の位置だけが違う。**

## 3. 座標が通る経路（故障しうる箇所の全体像）

```
[1] カメラセンサー（4032×3024・横長）
      │  AVCapturePhotoOutput。videoOrientation は未設定（既定 .portrait）
      ▼
[2] JPEGバイト（3024×4032・縦長、EXIF orientation=1）  ← 実測値
      │
      ├──[3] アプリ: UIImage(data:) → 表示に使う。UIImage.size で寸法を得る
      │
      └──[4] アプリ: バイトをそのままサーバーへ送信
                │
                ▼
          [5] サーバー: バイトから寸法を導出（JPEGヘッダ）
                │
                ▼
          [6] サーバー: 寸法をプロンプトでモデルに伝える
                │
                ▼
          [7] モデル: 正規化座標で枠を返す
                │
                ▼
          [8] アプリ: OverlayGeometry が
                    正規化座標 →（アスペクト比維持のレターボックス補正）→ 表示ポイント
                │
                ▼
          [9] SwiftUI: Image を scaledToFit で描画し、その上に枠を重ねる
```

**[3] と [5] が同じ寸法を指していること**、および **[8][9] が実際の描画領域と
一致していること**が正しさの条件。どこか1つ狂うと、例外は出ず、
**正しそうな答えが違う場所を指す**。

## 4. 確定している事実（測定済み）

| 事実 | 測定方法 |
|---|---|
| 実機写真は `stored=3024x4032` / `exif_orientation=1` / `bytes≈3.1MB` | サーバーの診断ログ（`[analyze]` 行） |
| `videoOrientation` はコード中で未設定。既定の `.portrait` | `grep -rn videoOrientation ios/` で0件 |
| **合成スクリーンショットではモデルの座標はほぼ完璧**: x誤差0.000 / y誤差0.000〜0.001 / IoU 0.969 / 枠の中心が対象内 8/8 | 正解座標が既知の1280×800画像で4要素×2回 |
| モデルに寸法を**誤って**伝えると、その分母で割った座標を返す | EXIF回転画像で `660÷1280=0.516` と返り値が完全一致 |
| サーバーは4032×3024でも3.4秒で応答。**サイズは速度上の問題ではない** | curl実測 |
| SSEの解析は正常（delta＋resultを取得できている） | ライブ接続で実測、result 1件を確認 |

## 5. 分かっていないこと（ここが空白）

**実機のカメラ写真に対して、モデルの座標が正しいのか一度も測っていない。**
測定は全て合成画像で行った。したがって次の2つを区別できていない。

- **モデルが返す座標が違う**（経路 [7] より前の問題）
- **アプリの描画が違う**（経路 [8][9] の問題）

**この空白を埋めないまま直そうとしたので2回外した。**

## 6. 仮説と、それを判定する測定

| # | 仮説 | 判定する測定 |
|---|---|---|
| H1 | モデルが写真（ベゼル・机・遠近が写る）では座標を外す。合成画像は綺麗すぎた | A |
| H2 | **モデルが「画面領域」を基準に正規化している。** 縦長写真の中に横長の画面が帯状に写るため、画像全体基準ではなく画面基準で答えている | A |
| H3 | `AnnotationOverlay` の `GeometryReader` が測る領域と、`Image` が実際に描かれる領域が一致していない | B |
| H4 | セーフエリアの扱いの差。画像はステータスバー下まで広がるが計測領域はそうでない（または逆）で、その分だけ上下にズレる | B |
| H5 | `.resizable().scaledToFit()` の実際の配置が `OverlayGeometry` の想定と違う | B |

**検討して除外した仮説**: `UIImage.size` が points で pixels でない場合。
縦横に同じ倍率がかかるだけでアスペクト比は変わらないため、レターボックス計算の
結果は変わらない。ズレの原因にならない。

## 7. 別問題として切り離すもの: 横持ち

`videoOrientation` が `.portrait` 固定なので、**端末を横にしてもプレビューも撮影も
回転しない**。横持ちを正しく動かすには回転を3箇所（プレビュー・撮影・座標変換）で
扱う必要がある。

**座標の調査中は縦持ちに固定して変数を減らすことを提案する**（現状横持ちは
壊れているので機能を失わない。あとで戻せる）。**これはレビュー対象の判断。**

---

## 8. 測定A: モデルの座標は正しいか

**アプリの描画を一切通さずに、モデル単体の精度を見る。**

### 手順

1. サーバーに、受け取った画像を保存し、**返ってきた枠を画像上に描き込んで**
   別ファイルとして出力する処理を足す（デバッグ時のみ有効にする）
2. 実機で1枚撮る
3. **出力された画像を人間が見る。** 枠が対象に乗っているか

### 判定

| 結果 | 意味 |
|---|---|
| 枠が対象に乗っている | モデルは正しい → 原因は経路 [8][9]（アプリの描画）。H3/H4/H5 |
| 枠がズレている | モデルの座標が違う → H1/H2。**アプリを触っても直らない** |

### 実装量

サーバー側のみ。画像へ矩形を描く処理が必要（Node なら `sharp`、または
デバッグ用途なので受信画像と座標をファイルに落として `python3` + PIL で
描くだけでもよい。**後者なら依存を増やさずに済む**）。

## 9. 測定B: アプリは既知の座標を正しく描けるか

**モデルを一切通さずに、描画だけを見る。**

### 手順

1. アプリに**キャリブレーション表示**を足す。モデルの結果ではなく、
   **決め打ちした正規化座標**の枠を描く:
   - 四隅: `(0,0,0.1,0.1)` `(0.9,0,0.1,0.1)` `(0,0.9,0.1,0.1)` `(0.9,0.9,0.1,0.1)`
   - 中央: `(0.45,0.45,0.1,0.1)`
2. 撮影後の画面でそれを表示する
3. **四隅の枠が写真の四隅に、中央の枠が中央に乗っているか**を見る

### 判定

| 結果 | 意味 |
|---|---|
| 四隅と中央に正しく乗る | アプリの描画は正しい → 原因はモデル側。H1/H2 |
| 乗らない | 描画がズレている。**ズレ方が原因を示す**（下記） |

### ズレ方から原因を読む

- **全体が一様に上下へずれる** → セーフエリア（H4）
- **上端は合うが下端がずれる** → 高さの取得元が違う（H3）
- **画像の外に出る枠がある** → `contentRect` の計算が実際の描画と不一致（H5）

## 10. AとBを合わせた判定表

| A（モデル） | B（描画） | 結論 |
|---|---|---|
| 乗る | 乗る | **両方正しい。** ズレの認識そのものを再確認する（ラベル位置の誤認など） |
| 乗る | 乗らない | **アプリの描画バグ。** H3/H4/H5 を上のズレ方で絞る |
| 乗らない | 乗る | **モデルの座標の問題。** H1/H2。プロンプトか入力画像の作り方で対処 |
| 乗らない | 乗らない | 独立した2つのバグ。**Bを先に直す**（Aの判定精度が上がる） |

## 11. 追加で取りたい計測値

アプリ内部が完全に見えていないので、**画面上にデバッグ表示**を出すのが早い
（Macに繋がずに読み取れる）。

- `UIImage.size` と `imageOrientation`
- `GeometryReader` が返す `proxy.size`
- `OverlayGeometry.contentRect`
- 受信した正規化座標そのもの

**サーバー側の診断ログは既に入れてある**（`[analyze]` 行で格納寸法・EXIF・
モデルへ伝えた寸法・返ってきた座標が出る）。これは残す。

## 12. 進める順序（提案）

1. **変数を減らす**: 縦持ち固定（§7。レビュー対象）
2. **測定Bを先に実施。** アプリ側は自分で完結して判定でき、モデル呼び出しの
   コストも待ち時間もかからない
3. **測定Aを実施**
4. §10の表で故障箇所を確定させる
5. **確定してから初めてコードを直す**

## 13. 第三者に見てほしい論点

1. **測定AとBで本当に切り分けられるか。** 見落としている故障箇所はないか
   （経路§3に段が足りていないか）
2. **H2（モデルが画面領域を基準に正規化している）は妥当な疑いか。**
   もっと直接的な確認方法があるか
3. **縦持ち固定は妥当な判断か。** 横持ちの回転対応を先にやるべきか
4. **測定Aの実装方法**: サーバーに画像処理の依存（`sharp`）を足すか、
   デバッグ用途なので受信画像を保存して手元のスクリプトで描くか
5. そもそも**この規模の問題に測定手順の定義から入るのは過剰か**。
   より短い道があれば知りたい

## 付録: 失敗した修正（繰り返さないために）

| 試したこと | なぜ外したか |
|---|---|
| **EXIF orientation を画素に焼き込む**（iOS側） | 合成画像では実在するバグを再現・修正できたが、**実機写真は `exif_orientation=1`** で該当しなかった。実機に対しては何もしないコード。症状が変わらなかったのは当然 |
| **横向きレイアウトの変更**（`AdaptiveSplit`） | 座標とは無関係。さらに横持ちを悪化させた（黒画面→横倒しの帯）。**巻き戻し済み** |

サーバー側のEXIF寸法読み取りは、他クライアント向けの防御として**残してある**
（害はなく、将来Macコンパニオンが送る画像に効く）。ただし**実機の症状の原因では
ない**ので、これを根拠に解決済みと判断しないこと。
