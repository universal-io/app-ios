# 引き継ぎ — 何を作り直さないか

作成: 2026-08-11（app-mac 開発セッションからの引き継ぎ）
対象: このリポジトリで開発を始めるエンジニア／セッション

まず [README.md](README.md) を読んでから本書へ来ること。READMEが「何を作るか」、
本書が「**すでに存在するものは何か**」と「**PoC仕様のどこが既存の決定と衝突するか**」を扱う。
目的は同じ発明を2度しないこと。

## 前提: 参照先 app-mac

本書は macOS版リポジトリ **[universal-io/app-mac](https://github.com/universal-io/app-mac)**
を `../app-mac/...` という相対パスで参照する。

すでに隣に `app-mac` がある環境なら、そのまま読める。無い場合だけ隣にcloneすること
（`git clone git@github.com:universal-io/app-mac.git`）。ブラウザで読んでいる場合、
相対パスのリンクは解決しないのでGitHub上で辿ること。

`app-mac` の中身:

| パス | 中身 |
|---|---|
| `BombSquad/` | macOSクライアント（Swift）。キャプチャ、AX走査、ハイライト、権限、診断 |
| `web/` | **Gateway**（Next.js）。全クライアント共通のサーバー。`api.universal-io.com` へデプロイされる |
| `docs/` | 設計・計画・検証手順の正本 |
| `README.md` | 現行プロダクトが「いまどう動くか」の正本 |

`../app-ios-legacy-bomb-squad` は開発終了した別プロダクト（iOSキーボード拡張）。
本企画には不要。調査ドキュメント2件だけ [docs/archive/](docs/archive/) に取り込んである。

## 0. これは2026-07-04に見送った企画ではない

[docs/archive/receiving-side-options.md](docs/archive/receiving-side-options.md) §0 は、
iOS受信側を「優先度低」と判断している。
理由は3つで、**いずれも「iPhoneが自分自身の画面を読む」前提**だった。

1. 汎用チャットAIにスクショを貼れば説明される。「見る→わかる」単体はコモディティ
2. 認知負荷の高い作業（役所・保険）はそもそもスマホでやらない
3. 業務ハーネスの価値がスマホには無い

本企画は「**iPhoneがMacの画面を映す**」ので、3つとも当てはまらない。作業はMacに残り、
業務の文脈も残り、汎用チャットAIは利用者のMacをミラーリングできない。当時
「iOSで実現可能な形として最も北極星に近い」と評価されたのは選択肢C（Broadcast Upload
Extension ＋ PiP のセッション型「認知の眼鏡」）だが、本構成はそれを裏返したものであり、
**App Review リスクとExtensionの50MBメモリ制限を回避したうえで同じ体験に到達する**。
前回のマップより筋が良い。

したがって旧ドキュメントの「優先度低」は本企画を止めない。ただし§1〜§4のiOS制約の分析
（サンドボックスはカーネルで強制、公式経路は4つ）は今も正しいので、将来iPhone自身の画面を
扱う話が出たときに読み直すこと。

## 1. 最重要の修正：iOSからVLMを直接呼ばない

PoC仕様は `VLMClient.swift` から OpenAI / Gemini を直接叩く構成になっている。**これは採用できない。**

Universal I/O のアーキテクチャ規則（`../app-mac/README.md`「本番アーキテクチャ」）:

> クライアントは AI プロバイダーを直接呼ばない。認証済みの全 AI リクエストは
> `https://api.universal-io.com` の本番 Gateway に送信する。

理由は設計上の趣味ではなく、直接呼ぶと次が全部壊れる。

| Gatewayが持っているもの | 直接呼ぶと |
|---|---|
| モデル選択とfallback（`web/lib/server/ai-routing.ts` が唯一の正本） | 経路が2箇所に分岐し、README記載の「正本1箇所」規則が崩れる |
| 認証・quota・利用数計上（`bs_usage_events`） | 課金もプラン制限も効かない |
| ZDR（`store: false`、OpenAI/Groqの管理画面設定） | データ保持の約束が守れない |
| Skills注入（Slack/Gmail/GA4/Stripe/アクティビティモニタ） | 精度レイヤーをゼロから作り直すことになる |
| プロンプト本体（`vision-prompt.ts`、mode解決、prompt injection対策） | 数か月分の調整を捨てる |
| APIキー | 端末に置くことになる（出荷不可） |

**`POST /api/ai/vision` をそのまま使う。** iOSクライアントが持つのは Supabase セッションだけで、
モデル名は知らない。これだけでストリーミング表示、二次モデルへのfallback通知、Skills、
利用計上が全部ついてくる。契約は `../app-mac/docs/api-contract.md`、呼び出し側の実装例は
`../app-mac/BombSquad/Services/GatewayVisionClient.swift`。

### Skills（精度レイヤー）が無料で付いてくる

Gatewayは画面上の製品を判定し、その製品固有の知識を注入する。ブラウザ内の製品はホスト名、
ネイティブアプリはbundle IDで判定する。現時点でSlack、Gmail、Google アナリティクス、Stripe、
アクティビティモニタに対応し、**1製品1ファイル＋登録1行**で増える
（`../app-mac/web/lib/server/skills/`）。

Skillsはデータであり制御フローに触れないので、該当しない画面でも汎用経路がそのまま動く。
**適用中のSkillは必ずUIに表示する**（見えない知識は疑うことも直すこともできないため）。
iOS側もこの表示義務を引き継ぐこと。

副次的な帰結として、**PoC仕様のモデル名は使わない**。`gpt-4o` / `gemini-1.5-flash` は
現行構成ではない（2026-08時点の一次は `gpt-5.6-luna`）。そしてモデル選定は
`ai-routing.ts` の1行変更なので、クライアント側の関心事ではない。

### モデル候補を試すときの必須スクリーニング

安いモデルを試すこと自体は正しい。ただし過去に Cerebras `gemma-4-31b` を試して打ち切った
実績があり（`../app-mac/docs/guidance-accuracy-plan.md`）、**打ち切り理由は「実機で開いた
プルダウンの中身を読めなかった」**こと。GA4も管理ツールも、目的の項目はメニューを開いて
初めて現れる。開いたメニューを読めないモデルは、遅延と単価がどれだけ優秀でも案内に使えない。
**新しいモデルを評価する最初のふるいはこれにする。**

## 2. アノテーション形式は既存のものより弱い

PoC仕様は `box_2d: [ymin, xmin, ymax, xmax]`（0〜1000正規化）を新規に定義しているが、
macOS側はすでに同じ問題を解いており、**その過程で「モデルが推定した座標」より良い方法に
到達している**。

現行の仕組み:

1. **0〜1000正規化グリッドはすでに存在する** — `NavigatorLocator` が
   `[[loc:x0,y0,x1,y1]]` を解釈する（`../app-mac/BombSquad/Models/ScreenshotAnnotation.swift`）。
   軸の順序だけが仕様と違う。新しい形式を作るなら既存と揃える理由を書くこと。
2. **AX候補方式のほうが強い** — macOSはAccessibilityで画面上の要素を走査し、
   role / label / 矩形を持つ候補一覧をモデルへ渡す。モデルは**候補IDを1つ選ぶだけ**で、
   座標を創作できない（Visionスキーマの `targetCandidateId` は供給されたIDのいずれかで
   なければならない）。自由記述の `box_2d` は、この制約を外す方向の変更になる。
3. **OCRで実測した矩形がモデルの推定に勝つ** — 「**何を**はVLMから、**どこに**は端末から」。
   ローカルOCRが対象ラベル文字列を見つけたら、その実測矩形がモデルの推定boxを上書きする。
4. **枠が出ない理由は3通りに分かれている** — `highlight=none`（モデルが対象を挙げなかった）／
   `unresolvable`（挙げたが画面上に置けなかった）／`resolved`（描画済み、以降は別の問題）。
   これを分けていないと「ハイライトが出ない」という報告に答えられない。

**本企画で効く帰結:** Macホストは引き続きAX走査ができる。フレームと一緒に候補一覧を
送れば、iOS側のハイライトは「VLMの当てずっぽう」ではなく**AX実測に接地した矩形**になる。
PoC仕様はこの可能性に触れていないが、精度の差は大きい。

## 3. Macホストは新規開発ではない

PoC仕様は `UniversalIO_Mac` を新ターゲットとして作る前提だが、必要な部品は
`../app-mac` にすでにあり、**実機で動いて公開まで到達している**（`v0.2.2`、2026-08-11公開）。

| 必要なもの | 既存実装 |
|---|---|
| 画面キャプチャ | `Services/ScreenshotCaptureService.swift`（ScreenCaptureKit、`SCShareableContent`） |
| どの画面を撮るか | `Services/ActiveDisplay.swift` — **カーソル位置ではなく前面アプリのフォーカスウインドウがある画面**。マルチディスプレイで見ていない画面を撮る事故を防ぐために到達した結論 |
| AX候補の収集 | `Services/VisionObservationCaptureService.swift`、`AXFocusSnapshotService.swift` |
| AXの高速化 | ノードあたり7往復→1往復（`AXUIElementCopyMultipleAttributeValues`）。実測2.3〜8倍、ばらつきも縮小 |
| 製品判定（Skills用シグナル） | `Services/BrowserHostLookup.swift` — ブラウザのホスト名を読む。パス・クエリは取得しない |
| Gateway通信 | `Services/GatewayVisionClient.swift`、`Core/GatewayClient.swift` |
| 権限の扱い | `Services/ScreenCapturePermission.swift`、`AccessibilityPermission.swift`、`PermissionsCoordinator.swift` |
| 診断・信頼性 | `Core/Diagnostics.swift`（R11。全操作に期限、無音終了の禁止） |

**送信解像度は実測済みなので再導出しない。** Retinaの生ピクセルで送ると画像トークンが
3.7倍（実測 7,756 → 2,032）。論理解像度（1ポイント=1ピクセル）まで落としても、開いた
メニュー11行を3回中3回読めた。**それ以下に落とすと精度が壊れ方が悪い** — 1/4では
ポート番号 `41411` を `4141` と読んだ。**黙って間違える。** ストリーミング表示用の解像度と、
解析に送るフレームの解像度は別に決めること。

## 4. 本当に新しいのはどこか（＝リスクはここに集中する）

上記を差し引くと、新規開発は実質2つしかない。

### 4-1. MultipeerConnectivity による Mac→iOS 映像伝送

**ここが唯一の未知数。** 最初のマイルストーンをここに置くこと。仕様の記述に事実誤認がある。

- **「同じApple ID」で繋がるわけではない。** MultipeerConnectivity は serviceType 文字列に
  よるローカルネットワーク＋Bluetoothの探索で、招待と受諾は明示的に扱う必要がある。
  Apple IDは関与しない。近くの他人の端末も探索対象になり得るので、ペアリングの設計が要る。
- **iOS 14+ はローカルネットワーク権限が必要**（`NSLocalNetworkUsageDescription`、
  および `NSBonjourServices` への serviceType 登録）。初回に許可ダイアログが出る。
- **1080p30 を100ms以下で通せるかは要実測。** MPCの帯域は潤沢ではなく、信頼配送
  （`.reliable`）で送ると混雑時にキューが伸びて遅延が累積する。`.unreliable` とフレーム
  破棄方針が要る。**ここが成立しなければ企画の形が変わる**ので、Step 1で測る。

**重要な設計上の逃げ道:** 映像ストリームと解析経路は分離できる。解析に必要なのは
「その瞬間の1フレーム」だけで、これはMacホストが直接Gatewayへ送れる。**映像が滑らかで
なくてもコパイロットは成立する。** 最悪、映像は低fpsのプレビューに退化させ、解析は
フル品質を保てる。この分離を最初から設計に入れておくと、MPCの実測結果に企画全体が
人質に取られない。

### 4-2. iOS側のオーバーレイ描画

`AVSampleBufferDisplayLayer` ＋ 透明な SwiftUI Canvas の2層。ここは仕様どおりで問題ない。
座標変換（正規化 → 表示ポイント）で注意すべきは、**アスペクト比維持のレターボックス分の
オフセット**を必ず挟むこと。macOS版の `ZoomableScreenshotView` が同じ変換を持っており
（正規化座標で保持し、描画時にだけポイントへ変換する）、拡大・パン中もハイライトが
ずれない構造になっている。読んでから書くこと。

## 5. リポジトリとGatewayの構造

**Gatewayは `../app-mac/web` にあり、`origin/main` へのpushが本番デプロイ**（Vercel git連携）。
つまり iOS 用にGatewayを変更すると、**macOSリポジトリのmainを押すことになる**。これは
既存の運用そのままだが、iOS開発で頻繁にGatewayを触るようになったら分離を検討する。

当面の推奨:

- **Gatewayは動かさない。** iOSからは `https://api.universal-io.com` を呼ぶだけにする。
  Vision routeは後方互換を保つ設計になっており（公開済みクライアント向けadapterの前例あり）、
  iOS用に新しいendpointを増やさない。**新surface・新endpoint・新model routeを作らない**のは
  R10で明文化された規則。
- 共有モデル定義（アノテーション型など）は、まずこのリポジトリ内に閉じる。両リポジトリで
  共有したくなったら、その時点でSwift Packageへ切り出す。先回りして作らない。
- このリポジトリはまだgit initされていない。最初のセッションで初期化すること。

`../app-ios`（旧）のキーボード拡張は本企画では使わない。旧設計では「返す」をiOSキーボードで
閉じる想定だったが、本企画では操作対象がMacなので、注入はmacOS側のCopilotが既に担っている。

## 6. 実装順序（PoC仕様のStepを差し替える）

| Step | 内容 | なぜこの順か |
|---|---|---|
| 1 | **MPCで1080p30を実測** — MacからiOSへ、遅延とフレーム落ちを数値で出す | 唯一の未知数。ここが崩れると企画の形が変わるので最初に潰す |
| 2 | iOS側の表示層（`AVSampleBufferDisplayLayer`）＋2層ZStack | 1が通れば素直に積める |
| 3 | **タップ → Macホストがその瞬間のフレームとAX候補をGatewayへ** → 結果をiOSへ返す | 解析経路。既存の `/api/ai/vision` をそのまま使う |
| 4 | オーバーレイ描画（正規化座標 → レターボックス補正 → Canvas） | 既存の座標変換を移植 |
| 5 | Copilotループ（操作後に再取得して次の一手） | macOS側の `copilot.capture`（変化検知＋整定待ち）の移植 |

Step 3で「Macホストが送る」としているのは、**AX候補・Skills判定に必要なシグナル
（bundle ID、ホスト名、ウインドウタイトル）がMac側にしかない**ため。iOSが画像だけを
Gatewayへ送る構成にすると、Skillsも AX接地ハイライトも効かなくなる。

## 7. 引き継がれる不変条件（macOS版で高い代償を払って得たもの）

- **ユーザーが指定した対象が回答対象である。** AX・OCR・画像はそれを取得する手段にすぎず、
  取得の成否がユーザーの意図を上書きしない。取得できなかったことを「対象が無い」と報告
  しない（R10.5。この誤りでリリースを1本止めている）。
- **不在と不明を区別する。** 観測主体を持たない推測状態を作らない。「見えなかった」と
  「無かった」は別。
- **どの操作も無音で終わらない。** 有限時間で結果か、原因を述べるエラーに到達する。
  取り消しにも理由を残す（R11）。
- **セッションの開始がUIの描画都合に依存しない。** SwiftUIのappearance callback 1点に
  依存させたことで、38時間稼働後にVisionが無音停止した。
- **プロンプトはドメイン中立に保つ。** 製品固有の語彙はSkills（データ）に置き、
  基礎プロンプトへ入れない。
- **長時間稼働の検証（D7）はリリースの必須ゲート。** 24時間超のプロセスで実操作を通す。
  形式ではなく、実際に欠陥を捕まえた実績がある（`../app-mac/docs/manual-golden-paths.md`）。

## 8. まだ決まっていないこと（設計の余地）

ここはゼロベースで考えてよい。既存の決定に縛られない。

- **接続とペアリングのUX** — MultipeerConnectivityは近くの他人の端末も探索し得る。
  どう選ばせ、どう記憶し、どう再接続するか。macOS版に前例が無い
- **iOS側の起動・呼び出し体験** — macOS版は右Shift 2回というグローバルホットキーを持つが、
  iOSにグローバルホットキーは存在しない。常時映しっぱなしなのか、セッション開始型なのか
- **質問の入力手段** — タップだけか、音声か、テキストか。Gatewayには
  `POST /api/ai/transcribe`（音声）が既にある
- **iPad と iPhone の扱い** — 画面サイズが大きく違う。同じレイアウトでよいか
- **Macホストの形** — 既存の macOS アプリに機能として同居させるか、別プロセスにするか。
  同居なら権限（画面収録・Accessibility）が既に取れている利点があるが、
  公開済みアプリの信頼性要件（R11）を背負う
- **オフライン・切断時の振る舞い** — 映像が切れた時に何を表示するか

## 9. 最初にやること

1. [README.md](README.md) と本書を読む
2. `../app-mac/README.md`（特に「本番アーキテクチャ」「操作」「データ保存」）を読む
3. `../app-mac/docs/design-philosophy.md`（北極星と作る順序）に目を通す
4. `git init` してXcodeプロジェクトの器を作る
5. **§6 Step 1（MultipeerConnectivityの実測）から着手する**

**測ってから決める。** このプロジェクトはそれで動いている。速そう・読めそうで判断せず、
実機で数値を取る。§4-1が通らなければ企画の形が変わるので、そこを最初に確かめる。

**分からないことは推測で進めない。** 環境変数、エンドポイント、認証の形、仕様が不明なときは
止めて確認する。
