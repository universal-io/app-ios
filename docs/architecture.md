作成: 2026-08-13 ／ ステータス: 設計中（コード未着手）

[README.md](../README.md) がプロダクト定義、本書がその実現方法。

## 1. 全体像

```
┌─ Mac コンパニオン（Broadcaster）──────────────┐
│  ScreenCaptureKit → VideoToolbox(H.264/HEVC)   │
│  ＋ AX候補スナップショット（任意・後述）        │
│  ＋ 画面メタデータ（アプリ名・ウインドウ名）    │
└──────────┬─────────────────────┘
           │ MultipeerConnectivity（ローカルP2P）
           ▼
┌─ iOS アプリ（プロダクト本体）─────────────────┐
│  ミラーモード: AVSampleBufferDisplayLayer       │
│  カメラモード: AVFoundation                     │
│  Overlay: 透明 SwiftUI Canvas（枠・吹き出し）   │
│  タップ / テキスト / 音声 → 解析要求            │
└──────────┬─────────────────────┘
           │ HTTPS
           ▼
┌─ API サーバー（新規・最小構成）────────────────┐
│  POST /api/analyze （SSEストリーミング）        │
│  ・AIプロバイダのキーはここだけが持つ           │
│  ・モデル選択と切り替えはここだけで行う         │
│  ・コンテキストパックの注入                     │
│  ・ベータトークン検証・レート制限               │
└────────────────────────────────┘
```

### 決定事項

1. **APIクライアントはiOSアプリのみ。** Macコンパニオンはサーバーと通信しない。
   カメラモード（Mac不在）と解析経路を1本化するため。
2. **AIプロバイダを端末から直接呼ばない。** キー保持・モデル選択・プロンプトは
   サーバー側の関心事。クライアントはモデル名を知らない。
3. **映像ストリームと解析経路は分離する。** 解析に必要なのは「その瞬間の1フレーム」
   だけ。ミラー映像がカクついても解析はフル品質を保てる。MPCの実測結果に
   企画全体が人質に取られないための構造。
4. **Macコンパニオンは薄く保つ。** キャプチャ・エンコード・送信・（任意で）AX候補
   添付のみ。状態もアカウントも持たない。

## 2. ミラーモード（映像伝送）

### トランスポート: MultipeerConnectivity

- serviceType 文字列によるローカルネットワーク＋Bluetooth探索。**Apple IDは関与しない。**
  近くの他人の端末も探索対象になり得るため、ペアリングUX（選択・記憶・再接続）を設計する
- iOS 14+ はローカルネットワーク権限が必要:
  `NSLocalNetworkUsageDescription` ＋ `NSBonjourServices` への serviceType 登録
- 映像フレームは `.unreliable` で送り、**古いフレームは捨てる**（信頼配送で送ると
  混雑時にキューが伸び遅延が累積する）。制御メッセージ（ペアリング、解析結果の通知など）
  は `.reliable`
- **1080p30を100ms以下で通せるかは未実測。** これが企画最大の未知数であり、
  最初のマイルストーン（roadmap M1）。不成立なら映像は低fps（例: 5fps）のプレビューに
  退化させる。解析経路は分離してあるので案内品質は落ちない

### 解析用フレーム

- ミラー表示用の解像度と、解析に送るフレームの解像度は**別に決める**
- 解析用フレームはMacの論理解像度（1ポイント=1ピクセル）を基準にする
  （根拠は [lessons-from-app-mac.md](lessons-from-app-mac.md) §3。それ以下に落とすと黙って誤読する）
- タップ時にiOSが保持している最新フレームを使うか、Macへ「今の生フレームをくれ」と
  要求するかは未決。後者の方が画質は確実だが往復が1回増える。M3で両方測って決める

## 3. カメラモード

- AVFoundationでカメラを起動し、シャッター（または自動安定検知）で静止画を取得
- 静止画に対して同じ `/api/analyze` を呼び、返ってきたアノテーションを静止画上に描画
- v1では**静止画ベース**とする（ライブカメラ映像への追従描画は、対象画面の傾き・
  台形歪み・手ブレ補正が必要で重い。延長線として記録のみ）
- ミラーモードとの差分は「AX候補・画面メタデータが無い」こと。純粋にビジョンだけで解析する

## 4. 解析API（サーバー契約）

### POST /api/analyze

リクエスト（`multipart/form-data` または JSON + base64。実装時に決定）:

```jsonc
{
  "request_id": "uuid",            // 必須。冪等性とログ突合
  "image": "<base64 PNG/JPEG>",    // 必須。解析対象の1フレーム
  "question": "ここはどうすれば？",  // 任意。無ければ画面の説明
  "tap_point": { "x": 0.42, "y": 0.77 },  // 任意。正規化座標(0-1)
  "turns": [ /* 直近の対話履歴、最大N件 */ ],
  "context_pack_id": "acme-erp-v2",       // 任意。適用するコンテキストパック
  "source": {                      // 任意。ミラーモード時のみ
    "kind": "mirror",              // "mirror" | "camera"
    "app_name": "...",
    "window_title": "...",
    "candidates": [                // Mac側AX候補（取れた場合のみ）
      { "id": "c1", "role": "button", "label": "送信",
        "box": { "x": 0.81, "y": 0.92, "w": 0.08, "h": 0.04 } }
    ]
  },
  "client": { "platform": "ios", "app_version": "0.1.0" }
}
```

レスポンス（SSE）:

| event | data | 意味 |
|---|---|---|
| `delta` | `{"text": "..."}` | 解説文の増分。表示専用 |
| `result` | 下記JSON | 検証済みの最終結果。**描画はこれだけを信じる** |
| `error` | `{"code": "...", "message": "..."}` | 失敗 |

`result`:

```jsonc
{
  "summary": "画面右下の『送信』ボタンを押します。",
  "annotations": [
    {
      "id": "a1",
      "kind": "highlight",           // "highlight" | "callout"
      "box": { "x": 0.81, "y": 0.92, "w": 0.08, "h": 0.04 },  // 正規化(0-1)、画像座標系
      "label": "ここをタップ",
      "candidate_id": "c1"           // AX候補に接地できた場合のみ
    }
  ],
  "applied_context_pack": "acme-erp-v2",   // null あり。UIに必ず表示する
  "meta": { "model_fallback_used": false }
}
```

### 契約の設計判断

- **ワイヤ座標は正規化float（0–1、画像左上原点、`{x,y,w,h}`）に統一する。**
  モデルが内部で何を出すか（0–1000グリッド等）はサーバーが吸収し、iOSに漏らさない。
  モデルを替えても契約が動かないようにするため
- **AX候補があるときは、モデルに候補IDを選ばせる。** 座標の創作を許さない方が精度が
  高いことはmacOS版で実証済み（lessons §4）。候補が無いとき（カメラモード等）だけ
  モデル推定boxにフォールバックする
- **適用中のコンテキストパックは必ずUIに表示する。** 見えない知識は疑うことも
  直すこともできない
- 枠が出ない理由は3値で区別する: モデルが対象を挙げなかった／挙げたが画面上に
  置けなかった／描画済み。これを分けないと「ハイライトが出ない」に答えられない

### サーバー実装方針

- 最小構成で新造する。技術スタックは Next.js (Vercel) を第一候補
  （運用経験が既にあるため）。ただし `/api/analyze` 1本＋管理系少々なので、
  実装時により軽い選択肢（Hono + Cloudflare Workersなど）と比較してよい
- モデルは1箇所（サーバー内のルーティング定義）で決め、一次＋二次フォールバックの
  2段まで。モデル評価の最初のふるいは「実機で開いたプルダウンの中身を読めるか」
  （lessons §5）
- プロバイダ側のデータ保持設定（ZDR相当）を最初から確認して選ぶ。B2B導線の生命線

## 5. 認証・課金・利用制御

### ベータ期（当面）

- 配布: TestFlight
- 認証: アカウント無し。**ビルドに埋め込んだベータトークン＋端末ID**をサーバーで検証し、
  レート制限をかける。トークンはサーバー側で失効可能にしておく
- 課金: 無し

### 製品期（方向性のみ。実装しない）

- 認証: Sign in with Apple
- 課金: StoreKit 2 サブスクリプション。レシート検証（App Store Server API）をサーバーで行い、
  エンタイトルメントをサーバー側で管理
- B2B: コンテキストパックの組織配布・管理コンソール。契約形態（VPP／カスタムApp／直接）は未決

## 6. コンテキストパック（差別化の中核）

- 実体は**サーバー側に置くテキスト（Markdown/YAML）**。プロンプトへの注入データであり、
  制御フローに触れない。該当しない画面では汎用経路がそのまま動く
- 構造（案）: パックID、対象システムの識別ヒント（アプリ名／画面の特徴）、
  操作知識（手順・禁止事項・用語）
- v1では**手作業でサーバーに配置**し、選択UIだけをiOSに作る。
  組織管理・アップロードUIはB2B検証が始まってから
- 基礎プロンプトはドメイン中立に保つ。製品固有・組織固有の語彙は必ずパック側に置く

---

## 7. セキュリティ・プライバシーの骨子

- 画面フレームは解析時のみサーバーへ送り、**サーバーに保存しない**（ログにも残さない）
- ミラー映像のP2P伝送はローカルネットワーク内で完結し、サーバーを経由しない
- Macの画面には第三者の情報（メール、顧客データ）が映り得る。プライバシーポリシーと
  App Privacy申告はこれを前提に書く
- B2B導入時の論点（データ処理契約、オンプレ／専用リージョン要求など）は導入検証時に詰める

## 8. 将来: リモート操作（設計メモのみ）

- iOS側の「これを押して」→ Macコンパニオンが `AXPress` 等で実行、という経路
- 必須の安全設計: 実行前のMac側確認（少なくとも初期は）、実行可能操作のホワイトリスト、
  すべての実行の監査ログ
- Macコンパニオンが「薄い送信専用」から「操作実行者」に変わるため、権限も信頼要件も
  一段重くなる。ミラー＋説明が価値を証明してから着手する
