# 実装ロードマップ

作成: 2026-08-13 ／ 最終更新: 2026-08-13（カメラ先行へ順序変更）

原則: **企画を殺しうるリスクから潰す。測ってから決める。**
各マイルストーンに「何が確認できたら次へ進むか」を書く。数値の合格ラインは
実測開始時に本書へ記入してから測る（測った後に基準を動かさないため）。

実測環境: MacBook Pro 16" 2021（M1 Pro / 16GB, macOS 26.5.2）＋ 手持ちのiPhone/iPad、同一Wi-Fi。

## なぜカメラモードが先か（順序の根拠）

当初はM1にMultipeerConnectivityの実測を置いていた。**変更した理由は、
[architecture.md](architecture.md) §1-3 で映像と解析を分離した時点で、MPCが
企画を殺しうるリスクではなくなったから。** MPCが不成立でも映像が低fpsに退化するだけで、
案内の品質は落ちない。

**企画を本当に殺しうるのは「AIが画面を見て有用な案内を返せるか」**であり、これは
カメラモードなら Macコンパニオン・MPC・ペアリングUX を一切作らずに検証できる。
さらにそこで作るもの — APIサーバー、オーバーレイ描画、座標系、対話UI — は
**ミラーモードでもそのまま使う背骨**であり、ミラーは後から「画像の入手元を差し替える」
だけになる。

## M1. カメラモードのエンドツーエンド ⚠️ 企画最大のリスクはここ

- カメラで画面を撮る → `/api/analyze` → ハイライト＋解説がその静止画上に出る
- 正規化座標→表示ポイント変換（**アスペクト比維持のレターボックス補正を必ず挟む**。
  lessons §6）

### 合格ライン

**枠の中心が対象要素の内側に入る率が 9/10 以上**、かつ体感レイテンシ5秒以内。
IoUではなく「中心が乗るか」を基準にするのは、利用者にとって枠が対象を指しているか
どうかが本質で、数ピクセルの一致度ではないため。

### 実測1: 合成スクリーンショット（2026-08-13、済）

正解座標が既知のフォーム画面（1280×800 JPEG）で4要素×2回。

| | 画像サイズを教えない | **教える（現行）** |
|---|---|---|
| 平均 \|x誤差\| | 0.000 | 0.000 |
| 平均 \|y誤差\| | **0.155** | **0.000** |
| 平均 IoU | ほぼ0 | **0.969** |
| 中心が対象内 | 0/8 | **8/8** |

レイテンシは平均2.7秒・最大4.7秒（`gpt-5.6-luna`、`reasoning.effort: "none"`）。

**判明した最重要事項**: モデルは画像サイズを教えないと、**実際の高さではなく
想定した高さ（約1080px）を分母にY正規化する**。x誤差ゼロ・y誤差0.155という
非対称な壊れ方になり、**解説文は正しいまま枠だけが別の行に出る** — 正解の顔をして
間違える種類の失敗。サイズはクライアントの申告ではなく
[server/lib/image-size.ts](../server/lib/image-size.ts) が画像バイトから導出する
（送り忘れを起こしえなくするため）。

### 実測2: 実機のカメラ写真（2026-08-14、初回実施）

iPhone 13でMacのXcode画面を撮影。

**案内の中身は成立している。** Xcodeのプロジェクト画面であることを正しく説明し、
表示されていた署名エラーについて「Signing & Capabilities で開発チームを選択する」という
**実際に正しい対処**を提示した（このリポジトリで人間が実行した手順と一致）。
汎用チャットAIにスクショを貼るのと比べて劣らない水準。

**ハイライトが下方向にズレていた（目視200〜300px）。** 最初はEXIF orientationを
疑い、合成画像で再現・修正したが、**それは実機の原因ではなかった**（実測3を見よ）。

### 切り分け（2026-08-14、済）

同一の見た目になる2枚を作って比較した。片方はEXIFなし（格納1280×800）、もう片方は
iPhoneの縦持ち写真と同じ構造（格納800×1280＋EXIF orientation=6 で表示時に回転）。

| 入力 | x | y（正解 0.825） |
|---|---|---|
| EXIFなし | 0.828 ✓ | 0.825 ✓ |
| **EXIF=6** | 0.829 ✓ | **0.516 ✗** |

**軸の入れ替わりではなかった。** `0.825 × 800 = 660px` を `660 ÷ 1280 = 0.516` —
返り値と完全一致した。つまり**モデルは回転後（1280×800）を見ているのに、サーバーは
格納時（800×1280）の寸法を伝えていた**ため、モデルが縦軸を誤った分母で割っていた。

実測1で見つけた「サイズを伝えないとY座標だけ壊れる」と**同じ穴の別の入り口**である。
サイズは伝えていたが、伝えた値が間違っていた。

### 修正（2箇所）

1. **iOSアプリで向きを画素に焼き込む**（本命）— 送るバイトと描画対象を同一の画像にする。
   これがないと「送った画像」と「枠を描く画像」が別の座標系になる
2. **サーバーはEXIF orientationを読んで寸法を入れ替える**（防御）— 将来のMacコンパニオンや
   他クライアントが回転画像を送っても静かに壊れないように

修正後、EXIF=6の画像でも `x=0.828 / y=0.825` と正解に完全一致することを確認済み。

**ただしEXIFは実機の症状の原因ではなかった。** 実機写真は `exif_orientation=1` で
該当しない。合成画像で再現したバグは実在するが別物で、修正を入れても症状は
変わらなかった。この修正は他クライアント向けの防御として残してある。

### 実測3: ズレの原因を確定（2026-08-14）

**サーバーが受け取ったバイトに、返した座標で枠を描いて人間が見る**という測定で
1枚で決着した。アプリの描画は正しく、モデルの座標が違っていた。詳細と外し方の
記録は [investigation-highlight-offset.md](investigation-highlight-offset.md)。

原因は2つで、どちらもアプリの座標変換ではなかった。

| # | 原因 | 実測 | 対処 |
|---|---|---|---|
| 1 | **送る画像が大きすぎた** | 実寸3024×4032で命中3/11・最大誤差0.448。1/2〜1/4で18/18・誤差0.005以内 | 長辺を1536に制限 |
| 2 | **座標をモデルに目測させていた** | 薄い横長のコントロールで +0.049 | OCRの実測矩形を `candidates` で渡す |

**誤差はバイモーダル**（当てるか大きく外すか）なので、定数オフセット補正は最悪手。

**「縮小すると数字を読み違える」という前提は逆だった。** 1/6まで縮めても
バージョン番号を正確に読む。アップロードは約4.5MB→0.2MBになり体感速度も上がった。
コストと帯域の課題も同時に解消している。

原因2の受け口（`candidates` / `candidate_id`）は**サーバーに最初から実装されていた**。
Macコンパニオンのアクセシビリティ実測を想定した設計で、カメラモードでは空のまま
だった。M5で予定していた「AX候補による接地」の考え方を、OCRでカメラモードに
前倒しした形になる。

**完了条件**: 枠の中心が対象内に入る率が 9/10 以上。**達成**（実機で全ハイライトが
対象に乗ることを確認）。

### M1で残したもの

- **文字のないアイコンボタンは接地できない。** 測る対象が無いためモデルの目測に戻る
- **枠が文字に吸い付き、文字が読みにくい。** 描画の調整で対応する（座標の問題ではない）
- **横持ちの座標は確認済み（合っている）が、実用にならない。** 画像が縦積み
  レイアウトの上半分に押し込まれるため文字が潰れ、**枠が合っているかを目視で
  判定することすら難しい**。座標ではなくレイアウトの問題
- **タップで対象を指定する経路が未接続。** `ContentView` の `pendingTap` は常に nil

### レイアウトの方針（M1の観察から）

**映像を常に全画面に敷き、UIはその上へオーバーレイする。** 現在は
`VStack { 画像; パネル }` で画面を分割しているため、横持ちで映像が潰れる。
ミラーモードは16:10の画面を扱うので同じ問題に必ず当たる。

**ただしカメラとミラーの両方の要求が見えてから一度で作る。** 以前
`AdaptiveSplit` を入れて横持ちを悪化させ巻き戻した前例がある（あのときは
座標バグの修正のつもりでレイアウトを触ったのが誤りだった）。

## M4. Macコンパニオンとミラーリング（MPC実測）

### 着手前に片付けること → 済（実測3）

**ズレの原因は座標系の食い違いではなかった。** 実測3の通り、(1)写真を実寸で送っていた
ことと、(2)座標をモデルに目測させていたことの2つで、**どちらもミラーモードには
そのまま持ち越さない**:

- ミラーはScreenCaptureKitの画面キャプチャで、**写真ではない**。実測3では合成画像を
  同じ3024×4032で送っても誤差0.000だった。サイズの崖は「写真かつ大きい」で起きる
- 接地はミラーの方が有利。OCRの代わりに**AXの実測矩形**を`candidates`に載せられる
  （M5の前倒しになる）

**ただし「カメラで出た答えがミラーでも成り立つ」と仮定しないこと。** 実測3の教訓は
まさに、合成画像で測った結果を写真に持ち越して2回外したことだった。ミラーでも
**サイズと精度は独自に測る**。Retinaキャプチャは3456×2234程度になるので、
長辺の制限が必要かどうかは測ってから決める（文字の可読性と両立させる必要がある）。

### すでに出来ていること（作り直さない）

M1〜M3で**解析の背骨は完成している**。ミラーモードで新しく要るのは映像の入手経路だけ。

| | 状態 |
|---|---|
| `POST /api/analyze`（SSE・構造化出力・コンテキストパック） | 完成 |
| 正規化座標の契約と画像サイズのサーバー側導出 | 完成 |
| iOS: SSE解析・オーバーレイ描画・レターボックス補正・対話 | 完成 |
| iOS: 画像の入手元 | **カメラのみ。ここにミラーを足す** |

### 実測4: キャプチャと帯域（2026-08-14、伝送は未着手）

MacBook Pro 16インチ（M1 Pro）、`mac/` のCLIで測定。**伝送を一切含まない**ので、
悪い結果をMPCのせいにもできないし、良い結果をMPCの手柄にもできない。

| | 動かした画面 | 静止した画面 |
|---|---|---|
| パイプラインの素の速度 | 28.9 samples/s | 30.8 samples/s |
| 実際に絵が変わった回数 | 23.6 fps | 5.2 fps |
| **帯域（H.264、上限8Mbps）** | **5.84 Mbps** | **0.33 Mbps** |
| 1フレーム | 平均30KB / 最大277KB | 平均8KB / 最大129KB |
| 圧縮の取りこぼし | 3/236 | 3/52 |
| 圧縮の待ち時間（行列込み） | 19.5ms | 20.7ms |

- **キャプチャは要求30に対して常に約30 samples/s出る。** 論理解像度1728×1117で、
  解析用に変換不要。初回フレームは43〜59ms
- **重要なのは静止時の列。** 「画面を見て操作を教わる」用途では画面はほぼ静止する。
  5.84 Mbpsは「10秒間スクロールし続けろ」と指示して作った**最悪値**
- **企画最大の未知数はかなり縮んだ。** 運ぶのは1080p30の生映像ではなく、
  よく圧縮された画面映像である

**未解決の問い**: 8Mbpsの上限に対して5.84Mbps出ているので、**上限を下げたときに
文字が読めるかは未測定**。合格ラインの第1項は可読性なので、伝送を作る前か後かは
別として、いずれ測る必要がある。

**測定器の欠陥を2つ踏んだ**（同期圧縮がキャプチャを詰まらせ、8.6fpsという嘘の値を出した／
「圧縮コスト」が実際は行列込みの待ち時間だった）。**測定器そのものを疑うこと。**

### 実測5: MPCの伝送（2026-08-15、映像は未使用）

実測4で得た**実フレーム相当の30KB**を、映像ではなくダミーで送って往復時間を測った。
iPhone 13 ⇄ MacBook Pro 16（同一Wi-Fi）。片道ではなく往復にしたのは、2台の時計を
合わせずに済ませるため（半分にするのは**仮定**であって測定ではない）。

| fps | 提供帯域 | pass 1 | pass 2 |
|---|---|---|---|
| 10 | 2.46 Mbps | 停止 0/100 | **停止 29/100、p95 2004ms** |
| 15 | 3.69 Mbps | **停止 129/150、p95 5313ms** | 停止 0/150 |
| 20 | 4.92 Mbps | **停止 79/200** | 停止 0/200 |
| **30** | **7.37 Mbps** | **停止 0/300、p95 61ms** | **停止 0/300、p95 68ms** |

**遅延は負荷と相関しない。** 最も重い30fpsが2周とも完璧で、最も軽い10fpsが2周目に
崩れている。負荷が原因なら起こりえない並びである。

- **MPCは7.37 Mbpsを往復60ms台で運べる。** 合格ライン（片道300ms）に対して
  片道約30msで、**約10倍の余裕**がある。実測4の動作時5.84 Mbpsもそのまま通る
- **損失は全レート・全パスで0%。** `.unreliable` は何も捨てなかった
- **ただし数秒単位で止まる。** pass 1の15fpsと20fps（連続する2回）に集中しており、
  負荷ではなく環境要因（Wi-FiとAWDLの競合など）と見るのが自然

### 実測6: 5分間の連続運転（2026-08-15）

30fps・30KB・7.37 Mbpsを5分間（9000個）流し続けた。

| 指標 | 実測 | 合格ライン | 判定 |
|---|---|---|---|
| 損失 | **0%**（9000/9000） | — | — |
| 往復 | p50 13ms / p95 45ms / 最大338ms | — | — |
| **片道（往復の半分・仮定）** | **p95 22ms**、最悪169ms | 300ms以内 | ✅ **13倍の余裕** |
| **接続** | **全区間で維持** | 5分間切断なし | ✅ |
| 200ms超の停止 | 48/9000（0.53%） | — | — |
| 30秒ごとの停止数 | 12 0 7 0 4 1 8 0 6 0 | — | — |

**実測5で見えた数秒単位の停止は再現しなかった**（今回の最悪は338ms）。あれは
計測器が見えていなかった切断に伴うものだった可能性が高い。ただし**停止自体は
全区間に散らばって実在する**ので、下記の設計要件は変わらない。

**直前の測定は「損失91%」と報告したが、実際は27秒での切断だった。**
計測器を直さずにいたら「MPCは使えない」と結論して企画の形を変えていた。

#### ここから確定した設計要件

1. **Broadcaster自身が送信を止める。** `.unreliable` を選んでも捨てられない。
   architecture §2 の「古いフレームは捨てる」は送信モードでは実現しない
2. **停止から復帰したら、溜まったフレームを再生せず最新へ飛ぶ。**
   5秒止まったあと5秒遅れの映像を流し続けることになる

#### 測定器の欠陥（3つ踏んだ。**計測器を疑うこと**）

- レート間で計測記録を消していたため、飛行中の応答が損失として数えられた
- 2fps・5fpsは標本が10〜25個しかなく、p95が「たまたま遅い1個」でしかなかった
- **iPhoneがスリープすると無音になる。** 「損失100%・遅延0ms」という
  データの顔をした行が出た

### やること

1. `mac/` にBroadcasterを新規作成。ScreenCaptureKit → VideoToolbox(H.264) →
   MultipeerConnectivity。**Macコンパニオンはサーバーと通信しない**（architecture.md §1）
2. iOS側に `AVSampleBufferDisplayLayer` を足し、解析へ渡す画像の供給元を差し替える
3. ペアリングUX（MPCは近くの他人の端末も探索する）。macOS版に前例が無い
4. **遅延・フレーム落ち・安定性を数値で出す。** 1080p30を基準にfps・解像度を振る。
   `.unreliable` ＋フレーム破棄方針（architecture.md §2）
5. Mac側にも `NSLocalNetworkUsageDescription` 相当と `NSBonjourServices` の登録が必要。
   iOS側も同様（**iOSは宣言が無いと許可を求めず、オフラインを装って失敗する**。M1で経験済み）

### 合格ライン（2026-08-14、測定前に記入）

**この製品の映像は操作用ではなく読解用**なので、fpsは最上位の指標ではない。
順に満たすこと。未達なら低fpsプレビュー構成へ退避する（映像と解析は分離済みなので
案内の品質は落ちない。architecture.md §1-3）。

| # | 指標 | 合格ライン | 結果 |
|---|---|---|---|
| 1 | **可読性** | ミラー表示のUI文字を、拡大せずに判読できる | **未測定**（実装後） |
| 2 | **遅延** | Macの画面変化→iOSに見えるまで p95 300ms以下 | ✅ 片道22ms（実測6） |
| 3 | **安定性** | 5分の連続使用で切断・ハングなし | ✅ 損失0%（実測6） |
| 4 | fps | 上記を満たした上での従属指標。**単独では合否を決めない** | 30fpsが通る |

**2と3は伝送単体での測定である。** 映像・デコード・描画を載せたら再測する。

**測った後にこの表を書き換えない。** 未達なら退避策を選ぶのであって、
基準を下げるのではない。

### 解析用フレームの解像度（測定前の方針）

**論理解像度（1ポイント=1ピクセル）を使い、そこからさらに縮小しない。**
根拠は lessons §3（Retina生ピクセルはトークンの無駄、1/4に落とすとポート番号
`41411` を `4141` と誤読）。

**カメラの1536制限をここへ持ち込まない。** あれは「写真」で測った値で、
実測3では合成画像なら3024×4032でも誤差0.000だった。なお開発機の論理解像度は
約1728×1117で、**実測3の良好域（1344〜2016）に元から収まっている**ため、
2つの教訓は衝突しない。**ただしミラーでも精度は独自に測る。**

**完了条件**: 「Macの画面をiPadで見て、タップしたら正しい場所に枠と説明が出る」。
**この結果が悪くても企画は死なない。**
